STAFF & PAYROLL (HR) MODULE — BUILD ROADMAP
Inventory Management System / Glory Desk
============================================

Status: PHASES 6-7 DONE (2026-08-17). Phases 8-10 not started. This file
tracks the build, phase by phase, the same way industry-roadmap.txt tracks
the rest of the product. Mark [x] only when a task is actually working
end-to-end, not when it's "mostly done" — that's how industry-roadmap.txt
ended up claiming things (mobile apps, SSO, SMS) that don't really work.

Conventions used throughout: Entity -> Service -> ViewModel -> View -> DI
wiring in App.axaml.cs -> nav entry + permission + license gate in
MainViewModel.cs -> tests -> docs. Copy an existing module (Suppliers is the
closest analogue) rather than inventing a new pattern.

Decisions baked into this plan — revisit if you disagree:
- Employee is its own entity, separate from User (login account). Staff who
  never log into Glory Desk (cleaners, drivers) still need payroll records.
  Employee has an optional UserId link for staff who also log in.
- Statutory numbers (PAYE bands, RSSB %, CBHI %) are editable settings, not
  hardcoded — rates change, and you may sell outside Rwanda later.
- License gating: Staff records at Medium+, Payroll processing at Pro+
  (matches how Forecasting/Audit Trail are gated today). Change if you want
  Payroll to be an Enterprise-only upsell instead.

    Pending/Rejected don't count)
[x] ViewModels/Views: AttendanceViewModel/View (daily register grid, one
    row per active employee, Status dropdown + notes, Save Day),
    LeaveRequestsViewModel/View (submit form, Pending Approval grid with
    Approve/Reject, per-employee history + live balance panel)
[x] DEVIATION: did NOT reuse WorkflowApprovalService/ApprovalRequest for
    leave approval. That table is a separate parallel status from
    LeaveRequest.Status — routing leave through it would mean two status
    fields that could drift out of sync for no real benefit here.
    LeaveService.ApproveAsync/RejectAsync directly own LeaveRequest.Status
    instead. Approving also calls AttendanceService.ApplyApprovedLeaveAsync
    to write OnLeave rows for every day in range — no double entry between
    the two features.
[ ] Reports: attendance summary (present/absent/late %) and leave balance
    report as standalone Report pages — NOT built. Today the same numbers
    only exist inline (AttendanceViewModel.SummaryText for one day/branch,
    LeaveRequestsViewModel.SelectedEmployeeBalances for one employee at a
    time). No cross-employee/period rollup report yet — add in Phase 9
    (Payroll Reporting) alongside the payroll reports, since they'll likely
    share a "Team & Settings > Reports" page.
[x] Tests: Phase7Tests.cs — 7 tests: leave types seeded, attendance
